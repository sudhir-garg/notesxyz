Learning roadmap

The central idea is simple: instead of training billions of existing model weights, train a much smaller set of additional parameters that learns the task-specific change.

LoRA

Keep the pretrained model weights fixed and learn a low-rank update using two smaller matrices.

QLoRA

Quantize the frozen base model—commonly to 4-bit—and train LoRA adapters on top.

Practical outcome

Lower trainable-parameter count and reduced memory requirements for adaptation.

One-sentence memory aid: LoRA reduces the number of parameters you train; QLoRA additionally reduces the memory used to store the frozen base model.
Section 01

Base models and fine-tuning

A base model (also called a pretrained model) has already learned general patterns from a large pretraining corpus. The corpus may contain text from sources such as books, websites, and other datasets. A language model uses the context it has received to predict the next token.

That general capability is useful, but an application often needs behavior specialized for a domain or a task. Fine-tuning continues training from the pretrained weights using a more targeted dataset.

Three levels of adaptation discussed in the lecture

General application adaptation

Adapting the base model to a desired assistant or application behavior.

Domain-specific fine-tuning

Specializing behavior for a domain such as finance, sales, or retail.

Task-specific fine-tuning

Teaching a narrower task such as document question answering or text-to-SQL.

Terminology clarification: “Domain-specific” and “task-specific” describe what the adaptation is for. “Full fine-tuning” and “LoRA” describe how the model parameters are updated. A domain-specific task can be trained with either full fine-tuning or LoRA.
Section 02

Why full-parameter fine-tuning becomes expensive

In full-parameter fine-tuning, the training process updates the pretrained model's weight matrices. If a model has billions of parameters, the optimization process must manage gradients and optimizer state for a very large parameter set, in addition to the model weights and activations.

Wnew = Wold − η · ∇WL

Here, L is the training loss, ∇WL is the gradient with respect to the weights, and η is the learning rate. In full fine-tuning, the trainable set includes the base-model weights.

Where the resource pressure comes from

Training memory

Model weights, gradients, optimizer states, activations, and temporary workspaces all consume accelerator memory.

Operational cost

Larger GPU memory capacity and compute throughput may be needed, increasing infrastructure cost.

The lecture uses a very large model (for example, 175 billion parameters) to illustrate why updating every parameter can become impractical for a limited GPU or RAM budget. The exact memory requirement depends on numeric precision, optimizer, batch size, sequence length, architecture, and implementation.

Section 03

Parameter-efficient fine-tuning (PEFT)

Parameter-efficient fine-tuning is a family of approaches that adapts a large pretrained model while training only a small fraction of its parameters. LoRA is one prominent approach in this family.

The goal is not to rebuild the entire pretrained model from scratch. Instead, preserve the pretrained knowledge and learn a compact task-specific update.

Full fine-tuning

Update the original model parameter tensors. It offers direct flexibility, but can require substantial memory and compute.

LoRA / PEFT

Freeze the base parameter tensors and optimize a smaller set of adapter parameters.

Keep these two questions separate: (1) Which model behavior should change? (domain or task objective) (2) Which parameters should be trainable? (full model or PEFT adapter)
Section 04

What exactly is LoRA?

LoRA stands for Low-Rank Adaptation. It is a parameter-efficient fine-tuning method in which the original pretrained weights are frozen and a trainable low-rank update is added to selected weight matrices.

Suppose a pretrained layer has weight matrix W₀. During full fine-tuning, we would learn an updated matrix directly. With LoRA, we keep W₀ fixed and represent the change using two smaller matrices.

W = W₀ + ΔW    where    ΔW = B A

In a commonly used LoRA parameterization, a scaling factor is also applied:

W = W₀ + (α / r) B A

W₀ is the frozen pretrained weight matrix. A and B are trainable low-rank matrices. r is the rank, and α controls the magnitude of the adapter update. The transcript's simplified equation focuses on W₀ + BA; the scaled version above is the common implementation form.

What “low rank” means intuitively

A matrix's rank describes the number of linearly independent directions represented by its rows or columns. A low-rank matrix can be expressed as the product of two narrower matrices. Instead of learning every entry in a large update matrix independently, LoRA constrains the update to a lower-dimensional structure.

Important: LoRA does not mean the original model matrix is replaced by two tiny matrices. The original matrix W₀ remains in the model. The two smaller matrices represent the trainable update added to it.
Section 05

The low-rank matrix mathematics

Worked example: a 3 × 3 update

Assume a layer's weight update is represented by a 3 × 3 matrix. A direct update contains nine scalar values.

ΔW ∈ ℝ3×3

For rank r = 1, LoRA can represent the update as:

B ∈ ℝ3×13 trainable values
A ∈ ℝ1×33 trainable values
B A = (3 × 1)(1 × 3) = 3 × 3Six scalar parameters generate a 3 × 3 update matrix.

For example, let:

B = [ 1   2   3 ]T,    A = [ 4   5   6 ]
BA =
[ 4   5   6 ]
[ 8   10   12 ]
[ 12   15   18 ]

The product has nine entries, but it was generated from only six trainable scalar values. This is the core compression idea behind the LoRA update.

Mathematical nuance: six values do not encode an arbitrary 3 × 3 matrix. A rank-1 product is constrained: every row and column is linearly dependent in the resulting matrix. LoRA trades unrestricted updates for a lower-dimensional update space. Larger ranks provide more expressive update capacity.

What changes when rank increases?

For a general update matrix of shape d × k, choose a rank r and use:

B ∈ ℝd×r,   A ∈ ℝr×k,   BA ∈ ℝd×k

As r increases, the update can represent a richer set of changes. But the number of trainable adapter parameters increases too.

Section 06

How many trainable parameters does LoRA save?

For a conventional dense matrix of shape d × k, full fine-tuning has d · k trainable entries for that matrix. LoRA's two matrices contain:

NLoRA = d r + r k = r(d + k)
Nfull = d k

When r is much smaller than both dimensions, r(d+k) can be much smaller than dk.

Numerical example: 4096 × 4096 matrix, rank 8

Full update

4096 × 4096 = 16,777,216

About 16.78 million trainable values for this one matrix.

LoRA update

8 × (4096 + 4096) = 65,536

65,536 trainable values across A and B.

Result for this one matrix: LoRA trains about 0.39% as many parameters as a full update, or roughly 256 times fewer. This is an illustrative layer-level calculation, not a universal whole-model percentage.

Why the whole-model total depends on configuration

In a Transformer, LoRA can be attached to selected projection matrices, such as query, key, value, and output projections. The total adapter size depends on:

  • How many layers receive adapters.
  • Which modules are targeted (for example, Q/V only versus Q/K/V/O).
  • The dimensions of those modules.
  • The rank selected for each adapter.

The lecture compares small adapter parameter counts against a very large full-model parameter count. Those counts are illustrative and configuration-specific; do not treat one reported percentage as a fixed property of LoRA.

Section 07

Choosing the LoRA rank (r)

The rank is a key hyperparameter. It determines the intermediate dimension of the adapter matrices and therefore affects both parameter count and adaptation capacity.

Rank choiceParameter costPotential behaviorWhen to consider it
Low rank (e.g. 1–4)LowerMore constrained update; less trainable capacityStart with a small adapter when the task is relatively narrow or resources are tight.
Moderate rank (e.g. 8–16)ModerateMore capacity while remaining parameter-efficientA practical starting range to experiment with; the lecture highlights rank 8 as a common example.
Higher rank (e.g. 32–64+)HigherCan represent more complex updates, but costs more memory and computeConsider when validation results indicate that a smaller adapter is underfitting.
Do not choose rank by intuition alone. Compare candidate ranks on a held-out validation set while keeping the data, training budget, and evaluation method controlled.

Other important LoRA configuration fields

  • r: adapter rank.
  • lora_alpha: scaling hyperparameter for the LoRA update.
  • lora_dropout: dropout applied on the adapter path during training.
  • target_modules: names of the model layers to which adapters are attached.
  • task_type: task family, such as causal language modeling.

The transcript points to Q/K/V projections in Transformer attention. In actual code, module names are architecture-dependent. Some models use names such as q_proj, k_proj, v_proj, and o_proj; others use different naming conventions.

Section 08

LoRA fine-tuning workflow

  1. Load a pretrained model. The base model already contains general language capabilities.
  2. Freeze the base weights. Prevent gradient updates to the original pretrained parameter tensors.
  3. Select target modules and rank. Decide which projection layers receive low-rank adapters and choose an initial rank.
  4. Initialize A and B. Add the trainable adapter matrices to the selected modules.
  5. Train on task-specific examples. Backpropagation updates the adapter parameters, not the frozen base weights.
  6. Evaluate and save. Measure task performance and save the adapter configuration and weights.
Section 09

What is QLoRA?

QLoRA combines low-rank adaptation with quantization. The pretrained base model is stored in a low-bit representation—commonly 4-bit—while LoRA adapters are trained on top of that frozen base.

The transcript describes a common configuration: load the base model in 4-bit using the bitsandbytes integration, use NF4 quantization, and perform computation/training with a higher-precision compute type such as FP16 or BF16.

NF4 and compute precision

  • 4-bit loading: stores the base-model weights using a 4-bit quantized representation.
  • NF4: a 4-bit quantization data type commonly used in QLoRA configurations.
  • Compute dtype: controls the precision used for computation. The transcript gives FP16 as an example; BF16 may also be available depending on hardware and model support.
  • Adapter parameters: remain trainable while the quantized base weights are kept frozen.
Precision clarification: A quantized model is not simply converted back into a permanently stored full FP16 model for every operation. Quantized weights are used by quantization-aware kernels, with values handled in the compute dtype as needed. The base remains represented in low-bit form in memory.

Why QLoRA helps

LoRA reduces the number of trainable parameters, but a large base model can still take substantial memory to load. QLoRA addresses that additional bottleneck by reducing the storage precision of the frozen base weights.

Simple memory estimate: 7 billion raw parameters at 4 bits each require approximately 3.5 GB for the packed weight values alone (7B × 4 ÷ 8). This excludes quantization metadata, non-quantized modules, activations, adapter weights, optimizer state, and runtime overhead, so actual GPU memory usage is higher.

Section 11

Practical code walkthrough: QLoRA with Hugging Face

The transcript demonstrates the core configuration ideas: load_in_4bit=True, NF4 quantization, a compute dtype, and a LoRA configuration with a chosen rank and target modules. The following example turns those ideas into a practical training scaffold.

Before running: install compatible versions of torch, transformers, peft, accelerate, bitsandbytes, and datasets. Choose a model you have permission to access. The target-module names below are common for LLaMA-like architectures; inspect your model and change them when necessary.
1 · Install the required packagesTerminal
pip install -U torch transformers peft accelerate bitsandbytes datasets
2 · Load a 4-bit base modelPython
import torch
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    BitsAndBytesConfig,
)

MODEL_ID = "your-authorized-causal-lm-model"

if not torch.cuda.is_available():
    raise RuntimeError("This 4-bit bitsandbytes QLoRA example expects a supported CUDA GPU.")

# Prefer BF16 when the installed GPU supports it; otherwise use FP16.
compute_dtype = (
    torch.bfloat16
    if torch.cuda.is_available() and torch.cuda.is_bf16_supported()
    else torch.float16
)

quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=compute_dtype,
    bnb_4bit_use_double_quant=True,
)

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    quantization_config=quant_config,
    device_map="auto",
)

model.config.use_cache = False

The NF4 and 4-bit settings reflect the QLoRA configuration discussed in the lecture. Double quantization is included as an optional memory optimization in common QLoRA setups; it is an implementation detail beyond the transcript's main explanation.

3 · Prepare the quantized model and attach LoRA adaptersPython
from peft import (
    LoraConfig,
    get_peft_model,
    prepare_model_for_kbit_training,
)

# Prepare the quantized model for adapter training.
model = prepare_model_for_kbit_training(model)

lora_config = LoraConfig(
    r=8,                         # rank
    lora_alpha=16,               # update scaling hyperparameter
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=[
        "q_proj",
        "k_proj",
        "v_proj",
        "o_proj",
    ],
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()

Interpretation of the important fields:

  • r=8 chooses the low-rank dimension highlighted in the lecture.
  • lora_alpha=16 sets the adapter scaling hyperparameter.
  • target_modules chooses which Transformer projections receive adapters.
  • task_type="CAUSAL_LM" declares the causal language-modeling task.
4 · Prepare a tiny illustrative text datasetPython
from datasets import Dataset

# Replace these examples with your own domain/task training data.
train_texts = [
    "Question: What is LoRA?\nAnswer: LoRA adapts a model using low-rank trainable updates.",
    "Question: What is QLoRA?\nAnswer: QLoRA combines a quantized frozen base with LoRA adapters.",
    "Question: What does rank control?\nAnswer: Rank controls the size and capacity of the low-rank update.",
]

raw_dataset = Dataset.from_dict({"text": train_texts})

def tokenize_batch(batch):
    return tokenizer(
        batch["text"],
        truncation=True,
        max_length=512,
    )

tokenized_dataset = raw_dataset.map(
    tokenize_batch,
    batched=True,
    remove_columns=["text"],
)
5 · Train the adapterPython
from transformers import Trainer, TrainingArguments

training_args = TrainingArguments(
    output_dir="./qlora-output",
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    learning_rate=2e-4,
    num_train_epochs=1,
    logging_steps=1,
    save_strategy="epoch",
    optim="adamw_torch",
    fp16=(compute_dtype == torch.float16),
    bf16=(compute_dtype == torch.bfloat16),
    report_to="none",
)

class CausalLMCollator:
    """Pad a batch and mask only padding positions in the labels."""
    def __init__(self, tokenizer):
        self.tokenizer = tokenizer

    def __call__(self, features):
        batch = self.tokenizer.pad(
            features, padding=True, return_tensors="pt"
        )
        labels = batch["input_ids"].clone()
        labels[batch["attention_mask"] == 0] = -100
        batch["labels"] = labels
        return batch

collator = CausalLMCollator(tokenizer)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset,
    data_collator=collator,
)

trainer.train()
6 · Save the adapterPython
ADAPTER_DIR = "./qlora-output/final-adapter"

model.save_pretrained(ADAPTER_DIR)
tokenizer.save_pretrained(ADAPTER_DIR)
Code-scope note: This is a compact end-to-end scaffold, not a production training recipe. The sample dataset is only for demonstrating the mechanics. Real fine-tuning requires a properly curated dataset, suitable prompt/response formatting, train/validation splits, task-specific evaluation, and hyperparameter tuning. Some model architectures need different target-module names or additional configuration.

Regular LoRA configuration (without 4-bit loading)

For standard LoRA, load the base model in a supported floating-point precision, then attach the same PEFT adapter configuration. You omit the BitsAndBytesConfig and the k-bit preparation step.

from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model
import torch

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
Section 12

Saving and using the trained adapter

One practical advantage of adapter-based tuning is that the adapter checkpoint is much smaller than a complete copy of the base model. To use it later, load the same base model and attach the saved adapter.

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel
import torch

BASE_MODEL_ID = "your-authorized-base-model"
ADAPTER_DIR = "./qlora-output/final-adapter"

base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL_ID,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

model = PeftModel.from_pretrained(base_model, ADAPTER_DIR)
tokenizer = AutoTokenizer.from_pretrained(ADAPTER_DIR)

prompt = "Explain low-rank adaptation in one paragraph."
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

with torch.no_grad():
    output_ids = model.generate(
        **inputs,
        max_new_tokens=120,
        do_sample=False,
    )

print(tokenizer.decode(output_ids[0], skip_special_tokens=True))

For a quantized deployment, load the base model with a compatible quantization configuration before attaching the adapter. Keep the base model identifier and adapter configuration together so the correct base checkpoint is used.

Section 13

Trade-offs and limitations

BenefitTrade-off / consideration
Far fewer trainable parameters than full fine-tuningAdapter capacity is constrained by the selected rank and target modules.
Smaller adapter checkpointsThe base model is still required for inference unless a deployment workflow merges or otherwise packages the adapter with it.
QLoRA lowers base-weight storage memoryQuantization may introduce numerical differences; evaluate task quality after fine-tuning.
Can make fine-tuning feasible on more modest hardwareMemory is not zero: activations, context length, batch size, optimizer state, and implementation overhead still matter.
Multiple adapters can represent different tasksAdapter selection, versioning, and base-model compatibility must be managed carefully.
Practical decision rule: Start with LoRA if the base model fits comfortably in memory. Consider QLoRA when loading the base model is the dominant memory constraint. Increase rank or broaden target modules only when evaluation suggests the adapter lacks enough capacity.
Section 14

Interview questions and answers

1. What is LoRA?

LoRA (Low-Rank Adaptation) is a parameter-efficient fine-tuning method. It freezes the pretrained model weights and learns a low-rank update represented by two smaller matrices, typically written as ΔW = BA.

2. Why is LoRA more parameter-efficient than full fine-tuning?

For a dense d × k matrix, a full update trains dk values. A rank-r LoRA update trains r(d+k) values. When r is small relative to d and k, this is much smaller.

3. What does the rank r control?

It controls the intermediate dimension of the low-rank factors and therefore the adapter's parameter count and representational capacity. Higher rank costs more but can represent richer updates.

4. What is the difference between LoRA and QLoRA?

LoRA freezes the base and trains low-rank adapters. QLoRA does the same while storing the frozen base in a quantized low-bit format, commonly 4-bit, to reduce memory use.

5. What is NF4?

NF4 is a 4-bit quantization data type used in common QLoRA configurations to represent the frozen base-model weights.

6. Why do we use a higher-precision compute dtype with 4-bit weights?

Low-bit quantization reduces storage, while computation may use a supported higher-precision type such as FP16 or BF16 for numerical operations. Storage precision and compute precision are separate configuration choices.

7. When would you increase the LoRA rank?

When validation suggests the current adapter is underfitting or the task requires a more expressive adaptation. Increasing rank should be tested against its added memory and compute cost.

8. What are target modules?

They are the specific model layers where LoRA adapters are inserted, commonly Transformer attention projections such as query, key, value, and output projections. Names vary by architecture.

9. Does LoRA reduce the base model's parameter count?

No. The pretrained base model remains intact and frozen. LoRA reduces the number of additional trainable parameters. QLoRA reduces the memory representation of the frozen base by quantizing it.

10. Does a rank-1 factorization reproduce every possible 3 × 3 update matrix?

No. A rank-1 product has a constrained structure. It can be generated from six values in the 3 × 1 and 1 × 3 factors, but it cannot represent an arbitrary 3 × 3 matrix. Higher rank provides more expressive capacity.

Concise interview summary

“LoRA freezes the pretrained model and learns a low-rank update using two smaller matrices, reducing the number of trainable parameters from roughly dk to r(d+k) for a targeted weight matrix. QLoRA combines this with low-bit quantization of the frozen base model—commonly 4-bit NF4—so fine-tuning requires less GPU memory.”
