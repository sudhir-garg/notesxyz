What you should understand by the end

Fine-tuning is the process of taking a model that already knows how to use language and training it further so that it behaves more reliably for a particular purpose.

Conceptual understanding

Understand base models, post-training, supervised fine-tuning, continued pretraining, preference optimization, and when to use each approach.

Technical understanding

Practical ability

Production readiness

Build a fair evaluation set, compare against the base model, deploy safely, monitor regressions, and version the result.

Central idea Fine-tuning does not mean building an LLM from zero. It means adapting an existing pretrained model by updating some or all of its parameters using additional training data.
01 · Fundamentals

1. What is LLM Fine-Tuning?

A Large Language Model is first pretrained on a very large corpus of text and other data. During pretraining, it learns statistical patterns that help it predict the next token. It develops broad language capability, general knowledge, and some reasoning patterns.

That general-purpose model may still not behave exactly as a business or application needs. It may return verbose answers when concise JSON is required, classify support tickets inconsistently, use the wrong terminology for a specialized domain, or fail to follow a particular response structure.

Fine-tuning continues training from the pretrained model using a smaller, carefully curated dataset that represents the task and behavior we want. The optimization process changes model weights (or a smaller set of adapter weights), making the desired behavior more likely on future inputs.

What actually changes?

For full fine-tuning, training updates the model's trainable parameters throughout the network. For parameter-efficient fine-tuning (PEFT), most original weights stay frozen and only a small number of newly introduced parameters are updated. In both cases, training attempts to reduce a loss function that measures how poorly the model predicts the desired target tokens.

Before fine-tuning

“I can answer many different kinds of questions, but my output style and task accuracy may be inconsistent for your specific workflow.”

After fine-tuning

“I have seen examples of this workflow and am more likely to respond using its expected terminology, decisions, and output format.”

What fine-tuning does not guarantee

  • It does not guarantee factual correctness or eliminate hallucinations.
  • It does not automatically give the model access to live databases, private files, APIs, or current information.
  • It does not guarantee that every piece of training data will be memorized or reliably recalled.
  • It does not replace application authorization, input validation, safety controls, or deterministic business rules.
02 · LLM lifecycle

2. Where Fine-Tuning Fits in LLM Development

Modern LLM development is usually described as a sequence of training stages. The terminology varies across research papers and vendors, but the following mental model is useful.

Pretraining

The model learns general patterns from a very large dataset, commonly by predicting the next token in a sequence. It is expensive and usually outside the scope of normal application teams.

Supervised fine-tuning (SFT)

The model is shown examples of desired behavior. A dataset might contain customer questions paired with ideal support answers, SQL requests paired with correct SQL, or incident descriptions paired with structured triage output.

Preference alignment

The model is trained to prefer responses judged better according to human or programmatic criteria. Examples include a helpful answer over an incomplete answer, or a concise answer over an unnecessarily long one.

Evaluation and deployment

Training is not proof of improvement. The candidate must be compared with the base model and current production baseline, tested on unseen examples, checked for regressions, and monitored after release.

03 · Architecture decision

3. Fine-Tuning vs Prompt Engineering vs RAG

These techniques solve different problems. They can also be combined. A common mistake is to fine-tune a model merely because it needs information that changes frequently.

ApproachWhat changes?Best suited forTypical limitation
Prompt engineeringInstructions and examples supplied at inference time.Clear instructions, role, output format, short task guidance, quick experimentation.Prompt can grow long; behavior may remain inconsistent; consumes context tokens.
RAGRelevant external documents are retrieved and placed in the model's context.Fresh, private, source-grounded or frequently updated knowledge.Retrieval quality, chunking, indexing and context assembly become additional failure points.
Fine-tuningModel weights or adapter weights are updated.Consistent style, task behavior, terminology, classification, structured outputs, specialized patterns.Needs high-quality examples, training infrastructure and ongoing evaluation; does not create a live knowledge connection.
Tool / function callingThe application gives the model access to controlled external functions.Actions such as querying a database, creating a ticket, calculating a value, or invoking an API.Requires secure tool design, permission checks, validation and reliable execution.

Decision guide

Rule of thumb If the answer must reflect a policy document updated yesterday, retrieve the latest policy. If the model must consistently transform an input into your organization's preferred schema, fine-tuning may help. If it must execute a payment or update a ticket, use a controlled tool with authorization.

Can RAG and fine-tuning work together?

Yes. Fine-tuning can teach the model how to interpret retrieved passages, cite evidence, follow domain-specific terminology, and produce a consistent answer format. RAG supplies the current facts. The combination can be more effective than either approach alone.

04 · Training methods

4. Types of Fine-Tuning and Post-Training

4.1 Continued pretraining (domain-adaptive pretraining)

The model continues next-token training on a large collection of domain text, such as technical manuals, research papers, financial documents, or code. The examples are often raw text rather than question-answer pairs.

Use it when: the model is weak at the language, vocabulary, syntax, or general patterns of a domain and you have a substantial, legally usable corpus.

Example: continuing training on a large corpus of engineering maintenance manuals before instruction-tuning the model to answer maintenance questions.

4.2 Supervised fine-tuning (SFT / instruction tuning)

The dataset contains input-output demonstrations. The model learns to generate the desired output after a prompt or conversation. SFT is the most common starting point for application-level fine-tuning.

Training example: prompt / conversation → target response

Typical uses include intent classification, extraction, response generation, summarization style, code transformation, structured JSON, and domain-specific instruction following.

4.3 Preference fine-tuning

Instead of showing only one ideal answer, the dataset records which of two or more possible answers is preferred. A preference example may contain a prompt, a chosen response, and a rejected response.

Preference training is useful when “good” is easier to rank than to write as a single exact target — for example, tone, helpfulness, completeness, or prioritization.

4.4 Reinforcement learning-based fine-tuning

The model generates outputs that receive scores from a reward function, grader, simulator, or expert evaluator. Optimization then increases the likelihood of outputs that receive higher rewards. The design of the reward signal is critical: a poorly designed reward can teach the model to exploit the metric rather than solve the intended task.

MethodTraining signalExample question
Continued pretrainingNext token in domain textCan the model better model domain-specific language?
SFTDemonstrated ideal answerCan it respond the way we want?
DPO / preference optimizationChosen vs rejected responseCan it prefer the better response?
RLHF / reward-driven tuningReward or graded outcomeCan it optimize a measurable objective across generated outputs?
05 · Parameter efficiency

5. Full Fine-Tuning, PEFT, LoRA and QLoRA

5.1 Full fine-tuning

In full fine-tuning, all (or nearly all) model parameters are updated. This offers high adaptation flexibility, but optimizer states, gradients, activations, and model weights can require substantial GPU memory. Storing a separate full copy for every task can also be expensive.

5.2 Parameter-Efficient Fine-Tuning (PEFT)

PEFT methods reduce training cost by updating only a small fraction of parameters. The original model is usually kept frozen, while a compact set of trainable parameters is added or selected. The resulting adapter can be stored separately from the base model.

Common PEFT families include LoRA and its variants, adapter layers, prompt tuning, prefix tuning, and selective layer tuning. PEFT often reduces compute and storage, but it is not guaranteed to match full fine-tuning on every task.

5.3 LoRA — Low-Rank Adaptation

LoRA is a widely used PEFT method. Instead of updating a large weight matrix directly, LoRA freezes the original matrix and learns a low-rank update using two smaller matrices.

W′ = W + ΔW    where   ΔW = (α / r) · B A

Here, W is the pretrained weight matrix, A and B are smaller trainable matrices, r is the rank, and α is a scaling parameter. Only A and B are trained. The rank controls the capacity of the adapter: a higher rank can represent a richer update, but generally uses more trainable parameters and memory.

LoRA parameters to recognize

  • r: low-rank dimension / adapter capacity.
  • lora_alpha: scaling factor for the update.
  • lora_dropout: dropout applied to the LoRA path during training.
  • target_modules: model layers into which LoRA adapters are inserted (for example, attention projection layers in some Transformer architectures).

5.4 QLoRA

QLoRA combines a quantized, frozen base model with trainable LoRA adapters. The base weights are commonly loaded in 4-bit form, while adapter parameters are trained at a suitable higher precision. Gradients pass through the frozen quantized model to update the adapters; the original quantized weights are not updated.

  • NF4: a 4-bit data type designed for normally distributed weights.
  • Double quantization: quantizes quantization constants to reduce memory overhead.
  • Paged optimizers: help manage memory spikes in supported training configurations.

QLoRA can make adaptation of larger models feasible on more modest GPU hardware. Actual capacity depends on model size, context length, batch size, GPU memory, attention implementation, and runtime settings.

MethodBase weightsTrainable parametersResource profileTypical reason to choose it
Full fine-tuningFull precision / mixed precisionMost or all model weightsHighest memory and compute demandNeed maximum adaptation capacity and have sufficient infrastructure.
LoRAUsually frozen, standard precisionSmall adapter matricesLower than full fine-tuningStrong practical default for task adaptation.
QLoRAFrozen, quantized (often 4-bit)LoRA adaptersLower base-model memory footprintGPU memory is constrained.
Prompt / prefix tuningFrozenLearned virtual tokens / prefixesVery small parameter updatesLightweight adaptation where method capacity is sufficient.
Practical starting point For many application teams adapting an open instruction model, LoRA is a sensible baseline. Try QLoRA when GPU memory is the main constraint. Consider full fine-tuning only after establishing a measurable need and confirming the compute budget.

6.2 Example: chat-style JSONL

JSON Lines (JSONL) stores one independent JSON object per line. For chat fine-tuning, a common representation is a messages array containing role/content pairs. The exact schema must match the trainer or provider being used.

train.jsonl — one example per line
{"messages":[
  {"role":"system","content":"You are a support-ticket classifier. Return only valid JSON."},
  {"role":"user","content":"The customer says they were charged twice for the same invoice."},
  {"role":"assistant","content":"{\"category\":\"billing\",\"priority\":\"medium\",\"needs_human\":true}"}
]}
{"messages":[
  {"role":"system","content":"You are a support-ticket classifier. Return only valid JSON."},
  {"role":"user","content":"The mobile application crashes immediately after login."},
  {"role":"assistant","content":"{\"category\":\"technical\",\"priority\":\"high\",\"needs_human\":true}"}
]}

The code block displays one JSON object with line breaks for readability; in a real JSONL file, place the entire object on one line. Put each additional object on the next line, without commas between records.

6.3 What makes a good example?

  • Realistic: resembles production inputs, including abbreviations, typos, ambiguity, and common edge cases where appropriate.
  • Correct: the target answer has been reviewed and is actually the behavior you want.
  • Complete: the answer does not rely on hidden information absent from the prompt or retrieved context.
  • Consistent: similar situations receive compatible labels, terminology, formatting, and decision rules.
  • Diverse: covers common examples, rare but important cases, different user styles, and negative examples when relevant.
  • Balanced: does not accidentally overrepresent one class, tone, refusal behavior, or response length.
  • Permitted: has a lawful basis for use and does not expose secrets or personal information unnecessarily.

6.4 Dataset splitting

Keep separate training, validation, and test sets. The training set updates the model. The validation set helps compare checkpoints and tune hyperparameters. The test set is reserved for final, relatively unbiased measurement.

SplitPurposeTypical use
TrainTeach the modelGradient updates during training.
ValidationGuide model selectionCheck loss, tune settings, identify overfitting.
Test / holdoutEstimate generalizationFinal comparison against baseline; never train on it.

A random split is not always sufficient. If near-duplicate tickets, conversations, documents, or users appear in multiple splits, the test score can be misleading. Consider grouping by customer, source document, time window, or conversation so related examples do not leak across the boundary.

6.5 Data cleaning and governance

  • Remove duplicate, corrupted, contradictory, irrelevant, and low-quality records.
  • Mask credentials, API keys, tokens, personal data, and confidential customer content unless a properly reviewed use case requires it.
  • Normalize labels and output schemas; validate JSON when JSON is the target.
  • Track provenance, collection date, license, consent or legal basis, and transformation history.
  • Keep a data-quality report with counts by category, source, language, length, and split.
Data leakage warning Never place examples from the final evaluation set into training, including paraphrased or near-duplicate versions. Leakage can make a fine-tuned model appear much better than it is in real use.
07 · Text representation

7. Tokenization, Chat Templates and Loss Masking

7.1 Tokens are not the same as words

LLMs process token IDs rather than raw text. A tokenizer may split one word into multiple subword tokens, while punctuation, whitespace, code, and multilingual text may be represented in different ways. Context length is measured in tokens, not characters or words.

During preprocessing, raw strings are converted to token IDs. The model receives a sequence such as [101, 392, 1845, ...] (illustrative only), and predicts a probability distribution for the next token at each position.

7.2 Chat template

Instruction models often use a model-specific template to encode roles and turn boundaries. The template may insert special tokens to mark system, user and assistant messages, and indicate where an assistant response ends or where a tool handoff occurs.

Rendered conversation = role markers + message content + turn / control tokens

Use the template expected by the chosen model. A dataset that looks valid as plain text may be formatted incorrectly for a chat model. When possible, use the tokenizer's chat-template utility rather than manually inventing role markers.

7.3 Labels and loss masking

For causal language-model training, token labels usually represent the next-token targets. In chat instruction tuning, a common objective is to compute loss on assistant target tokens while masking user and system prompt tokens with an ignore index. Some training configurations instead calculate loss over the whole concatenated sequence. Understand which behavior your trainer uses.

Why masking matters The model should learn what a good assistant response looks like. Accidentally training it to reproduce user messages or system instructions as target completions can waste capacity and produce undesirable behavior.

7.4 Truncation, padding and packing

  • Truncation: cuts sequences that exceed the configured maximum length. Check that it does not remove the answer or critical context.
  • Padding: makes examples in a batch the same length. Padding tokens should be handled correctly by the attention mask and loss labels.
  • Packing: combines shorter examples into a sequence to reduce unused context space. Use it only when the trainer handles example boundaries correctly.
  • Context length: choose a limit that covers real production inputs without needlessly increasing memory use.
08 · Optimization mechanics

8. How Fine-Tuning Works Internally

8.1 Forward pass

The model receives tokenized input and produces logits: unnormalized scores for the possible next tokens at each position. Applying softmax converts logits into probabilities.

8.2 Loss calculation

For next-token prediction, the standard objective is cross-entropy loss. It penalizes the model when it assigns low probability to the correct next token. With masked labels, ignored tokens do not contribute to the loss.

L = − Σt ∈ target positions log Pθ(yt | y<t)

Here, θ represents trainable parameters and yt is the correct target token at position t. The objective is to make the desired continuation more probable.

8.3 Backpropagation and optimizer update

Backpropagation computes gradients of the loss with respect to trainable parameters. An optimizer such as AdamW uses those gradients to update the parameters. With LoRA, gradients update the adapter matrices; frozen base weights remain unchanged.

8.4 Important training terms

TermMeaningWhat to watch
EpochOne pass over the training dataset.Too many epochs can cause memorization and reduced generalization.
Batch sizeNumber of examples processed together for one forward/backward pass.Limited by GPU memory and sequence length.
Gradient accumulationAccumulates gradients over multiple micro-batches before an optimizer update.Raises effective batch size without holding the full batch in memory.
Learning rateControls the scale of optimizer updates.Too high can destabilize training; too low can make learning ineffective or slow.
WarmupGradually increases learning rate at the start.Can reduce unstable early updates.
Weight decayRegularization applied by the optimizer to discourage overly large weights.Its useful setting depends on the model and training recipe.
CheckpointSaved model state at a particular training step or epoch.Allows rollback and comparison of intermediate models.
PerplexityExponential of average token-level cross-entropy loss.Useful for language modeling, but not sufficient as an application quality metric.

8.5 Overfitting and catastrophic forgetting

Overfitting occurs when the model performs well on training examples but poorly on unseen examples. Training loss may keep falling while validation quality gets worse. Catastrophic forgetting describes loss of previously learned capabilities after further training on a narrower distribution.

Mitigations include better data diversity, fewer epochs, lower learning rates, early stopping, smaller or more conservative updates, mixing representative data, and testing general capabilities that must be retained.

8.6 Effective batch size and training telemetry

When gradient accumulation or multiple GPUs are used, the micro-batch size is not the same as the effective batch size used for an optimizer update.

Effective batch size = per-device batch size × gradient accumulation steps × number of devices

Example: 2 examples per device × 4 accumulation steps × 2 GPUs = an effective batch size of 16, assuming the distributed trainer counts devices in the usual way.

Monitor more than loss: inspect the learning-rate schedule, gradient norms, GPU memory and utilization, tokens per second, data-loader throughput, checkpoint health, and validation metrics. For reward-based training, also inspect reward distributions, grader failures, and signs of reward hacking.

09 · Delivery process

9. End-to-End Fine-Tuning Workflow

  1. Define the task and success criteria.
    State the desired behavior, expected input distribution, output schema, unacceptable errors, latency needs, and business metric.
  2. Establish a baseline.
    Test the base model with a well-designed prompt. Record quality, latency, token usage, and cost before changing anything.
  3. Build an evaluation set first.
    Prepare representative examples, including edge cases. Keep a holdout set separate from training data.
  4. Collect and curate training data.
    Use expert demonstrations, reviewed historical examples, or carefully validated synthetic examples. Remove leakage and sensitive information.
  5. Select the base model.
    Check task fit, context length, tokenizer and chat template, language support, license, commercial-use conditions, hardware requirements, and deployment options.
  6. Choose a tuning method.
    Start with SFT. Use LoRA as a practical baseline, QLoRA for memory-constrained setups, and preference optimization if ranked outputs are needed.
  7. Train and track experiments.
    Record dataset version, base-model revision, library versions, hyperparameters, random seed, hardware, checkpoints, and metrics.
  8. Evaluate against the baseline.
    Compare task quality, regression cases, safety, latency, memory, and cost. Use human review where automatic metrics are inadequate.
  9. Package and deploy.
    Version the adapter or merged model, tokenizer, chat template, inference configuration, and any required metadata.
  10. Monitor and iterate.
    Track real-world performance, new error categories, distribution shift, user feedback, and rollback criteria. Add reviewed examples to the next training cycle.
Use an evaluation-first loop Define the tests before training. Otherwise, it is easy to mistake a model that produces more convincing-looking answers for a model that is actually more correct.

10.4 Training script — LoRA SFT

The example uses TRL's SFTTrainer with a conversational dataset and PEFT's LoraConfig. The configuration is a starting template, not a universal recipe. Confirm that your model supports the listed target modules and that your installed TRL version exposes the parameters used below.

train_lora.py
import os
import torch
from datasets import load_dataset
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, TaskType
from trl import SFTConfig, SFTTrainer

# Replace with a model you are permitted to use.
MODEL_ID = "Qwen/Qwen2.5-1.5B-Instruct"
OUTPUT_DIR = "./outputs/support-ticket-lora"


def main() -> None:
    if not torch.cuda.is_available():
        raise RuntimeError(
            "This example expects a CUDA GPU. Adapt the setup for your hardware."
        )

    # JSONL records should contain a conversational `messages` field.
    datasets = load_dataset(
        "json",
        data_files={
            "train": "data/train.jsonl",
            "validation": "data/validation.jsonl",
        },
    )

    tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
    if tokenizer.pad_token is None:
        tokenizer.pad_token = tokenizer.eos_token

    model = AutoModelForCausalLM.from_pretrained(
        MODEL_ID,
        torch_dtype="auto",
    )
    model.config.use_cache = False  # recommended during gradient-based training

    # These module names are architecture-dependent. Inspect the model first.
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=16,
        lora_alpha=32,
        lora_dropout=0.05,
        target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
        bias="none",
    )

    training_args = SFTConfig(
        output_dir=OUTPUT_DIR,
        num_train_epochs=2,
        per_device_train_batch_size=1,
        per_device_eval_batch_size=1,
        gradient_accumulation_steps=8,
        learning_rate=2e-4,
        logging_steps=10,
        eval_strategy="steps",
        eval_steps=100,
        save_steps=100,
        save_total_limit=2,
        weight_decay=0.01,
        warmup_ratio=0.03,
        # Confirm these options against your installed TRL version.
        max_length=2048,
        report_to="none",
        fp16=not torch.cuda.is_bf16_supported(),
        bf16=torch.cuda.is_bf16_supported(),
    )

    trainer = SFTTrainer(
        model=model,
        args=training_args,
        train_dataset=datasets["train"],
        eval_dataset=datasets["validation"],
        processing_class=tokenizer,
        peft_config=lora_config,
    )

    trainer.train()
    trainer.save_model(OUTPUT_DIR)
    tokenizer.save_pretrained(OUTPUT_DIR)
    print(f"Adapter/model artifacts saved to: {OUTPUT_DIR}")


if __name__ == "__main__":
    main()
Important implementation checks This is a reference training template, not a guarantee that every model works unchanged. Verify the model's chat template, LoRA target module names, precision support, TRL version, dataset schema, evaluation argument names, and loss-masking behavior before running a full job. For conversational SFT, consider assistant-only loss when the chat template and trainer support it.

10.5 Run training

python train_lora.py

The trainer reads batches, applies the model's chat formatting, calculates the language-modeling loss, updates LoRA parameters, evaluates on the validation split, and writes checkpoints. Monitor GPU memory, training loss, validation loss, throughput, and any warnings from the tokenizer or trainer.

10.6 QLoRA loading pattern

QLoRA adds a quantized base-model loading step before attaching the same type of LoRA adapter. The exact quantization setup depends on GPU and library compatibility.

Illustrative QLoRA setup
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import prepare_model_for_kbit_training

quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=(
        torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
    ),
)

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    quantization_config=quant_config,
    device_map="auto",
)

# Prepare the quantized base model before adapter training.
model = prepare_model_for_kbit_training(model)

# Pass this model and the same architecture-appropriate LoraConfig
# to SFTTrainer. Do not attempt to update the frozen 4-bit base weights.

10.8 Load the saved LoRA adapter for inference

Training produces an adapter artifact. At inference time, load the compatible base model first, then attach the saved adapter. The base model revision, tokenizer, and chat template must match the training setup.

inference.py · Load and query the adapter
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

BASE_MODEL_ID = "Qwen/Qwen2.5-1.5B-Instruct"
ADAPTER_DIR = "./outputs/support-ticket-lora"

tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL_ID)
base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL_ID,
    torch_dtype="auto",
    device_map="auto",
)
model = PeftModel.from_pretrained(base_model, ADAPTER_DIR)
model.eval()

messages = [
    {"role": "system", "content": "Classify the support ticket. Return JSON only."},
    {"role": "user", "content": "I was charged twice for my subscription."},
]

prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

with torch.no_grad():
    output_ids = model.generate(
        **inputs,
        max_new_tokens=120,
        do_sample=False,
    )

new_tokens = output_ids[0, inputs["input_ids"].shape[1]:]
print(tokenizer.decode(new_tokens, skip_special_tokens=True))
Inference compatibility check The adapter is not a standalone model. Keep the compatible base model and revision available. Validate the generated result with a JSON parser and application schema rather than assuming that training guarantees valid JSON.
11 · Alignment methods

11. Preference Tuning: RLHF and DPO

11.1 Why preference tuning?

For many generation tasks, several answers may be factually acceptable, but one is more useful, concise, complete, polite, or aligned with policy. A single gold answer may not capture all of those nuances. Preference data records which answer is better for a given prompt.

Preference example — conceptual JSON
{
  "prompt": "Explain why a data pipeline failed.",
  "chosen": "The job failed because the source file was missing. The next step is to verify the upstream delivery and retry after the file arrives.",
  "rejected": "The pipeline is broken. Try again."
}

11.2 RLHF — Reinforcement Learning from Human Feedback

A widely known RLHF pipeline contains three conceptual stages:

  1. SFT warm start: train the pretrained model on demonstrations of desired responses.
  2. Reward model: collect human rankings of candidate responses and train a model to score response quality.
  3. Reinforcement learning: optimize the language model to produce responses with higher reward while constraining it from drifting too far from a reference model.

11.3 DPO — Direct Preference Optimization

DPO trains directly on preferred and dispreferred responses using a preference objective. In its original formulation, it uses a reference policy and transforms the preference-learning problem into a classification-like loss. This avoids the need to separately fit a reward model and run an online RL optimization loop in the standard way.

Conceptually, DPO increases the relative likelihood of the chosen response over the rejected response for the same prompt, while controlling deviation relative to a reference model.

DimensionClassic RLHF-style pipelineDPO
DataDemonstrations, rankings / preferences, reward targetsPrompt, chosen response, rejected response
Reward modelCommonly trained as a separate stageNo separate reward model required in the standard DPO method
OptimizationOften a reinforcement learning algorithm such as PPODirect preference objective
Trade-offFlexible but can be more complex to operateOften simpler, but still sensitive to data quality and hyperparameters

Preference tuning is not a substitute for factual grounding or task-specific correctness checks. A preference dataset can teach an answer style while unintentionally rewarding confident but incorrect outputs if annotators or reward criteria are weak.

12 · Measurement

12. Evaluating a Fine-Tuned Model

Always evaluate the fine-tuned model against at least the base model with a production-representative prompt, and ideally against the current production system. Do not use training loss alone to decide whether the fine-tune is successful.

12.1 Evaluation dimensions

Task quality

Accuracy, precision, recall, F1, exact match, schema validity, code tests, or task-specific correctness.

Generation quality

Faithfulness, relevance, completeness, clarity, tone, style and instruction following.

Robustness

Unseen phrasing, typos, ambiguity, long inputs, edge cases, adversarial prompts and distribution shift.

Safety and privacy

PII leakage, secret reproduction, unsafe responses, over-refusal, policy compliance and prompt-injection resilience.

Operational metrics

Latency, tokens per second, GPU memory, throughput, failure rate, serving cost and uptime.

Retention

Check that useful general capabilities have not degraded after narrow-domain training.

12.2 Classification metrics

For classification or extraction tasks with reference labels, use deterministic metrics whenever possible.

Precision = TP / (TP + FP)    Recall = TP / (TP + FN)
F1 = 2 × (Precision × Recall) / (Precision + Recall)

Accuracy is useful when classes are reasonably balanced. For rare important classes, precision, recall, F1, per-class results, and a confusion matrix are usually more informative.

12.3 Generative-task evaluation

Many correct answers can have different wording. Exact string matching is then too strict. Use a rubric covering factual correctness, relevance, evidence use, format, and completeness. Combine deterministic checks, expert human review, and model-based graders when appropriate. Calibrate model graders against human judgments because graders can also be biased or inconsistent.

12.4 A/B and paired comparison

Run the same held-out prompts through the base and fine-tuned models under controlled decoding settings. Compare outputs side by side, ideally blind to model identity. For production, use a staged rollout or shadow traffic before replacing the current model.

12.5 Minimum experiment report

  • Base model and exact revision documented.
  • Training, validation and test set versions recorded.
  • Task metrics compared to the base model and production baseline.
  • Representative qualitative examples reviewed by humans.
  • Safety, privacy, and capability-retention tests completed.
  • Latency, hardware footprint and cost measured.
  • Known failure cases, rollback plan and release owner documented.
13 · Production

13. Deploying and Operating a Fine-Tuned Model

13.1 Adapter versus merged model

With PEFT, the fine-tuned artifact is often an adapter that is loaded alongside its compatible base model. This makes it possible to keep multiple task-specific adapters for one base model. Some workflows merge the adapter update into the base weights to simplify serving. Merging may affect quantization and storage choices, so test the final artifact using the intended inference stack.

Deployment styleAdvantagesConsiderations
Base model + adapterSmall task-specific artifact; can swap supported adapters.Serve the exact compatible base model and adapter; runtime must support PEFT.
Merged modelCan simplify serving with engines expecting standalone model weights.Larger artifact; merging and quantization may need extra validation.

13.2 Production architecture

13.3 Versioning and reproducibility

Treat the model like a software release. Version the base model, adapter, dataset, tokenizer, chat template, inference parameters, and evaluation report. Record the environment and package versions. Store large artifacts in a controlled registry or object store and apply access policies.

13.4 Monitoring

  • Quality: sample outputs, user corrections, escalation rates, and task-specific success metrics.
  • Drift: changing input patterns, new product names, new document types, or language shifts.
  • Operations: latency percentiles, throughput, memory, GPU utilization, error rates, and cost per request.
  • Safety: unexpected disclosures, refusal behavior, prompt injection, and policy violations.

13.5 Rollback

Keep the previous model version available. Define objective rollback triggers before rollout, such as a drop in high-priority class recall, unacceptable format failure rate, elevated latency, or a safety regression. The serving layer should be able to route traffic back to the known-good version.

15 · Worked example

15. Example: Fine-Tuning a DataOps Incident Assistant

Consider an internal assistant that classifies pipeline failures and returns a consistent triage summary. This example is illustrative; it does not assume access to any real organization’s data.

Problem statement

Inputs are incident descriptions such as “SFTP delivery missing”, “database connection timed out”, or “schema mismatch after deployment”. The assistant should return a structured category, priority, likely next check, and escalation flag.

Choose the architecture

  • Fine-tuning teaches the incident taxonomy, terminology, response format, and triage style.
  • RAG retrieves the latest runbooks, dependency maps, and service ownership information.
  • Tools perform controlled read-only checks, such as querying job status or retrieving logs.
  • Authorization is enforced by the application, not by the model's text response.

Example input and output

Input

“The hourly ingestion DAG failed because the upstream SFTP file was not present. The next run is in 40 minutes.”

Target output

{"category":"source_delivery","priority":"high","next_check":"Confirm upstream delivery and expected file name","escalate":false}

Dataset design

Collect reviewed examples across the major categories: source delivery, connectivity, credentials, schema, data quality, resource exhaustion, orchestration, and unknown/ambiguous. Include examples that should not be automatically classified when evidence is insufficient.

Evaluation design

Use per-class precision and recall, JSON parse success, correctness of the next check, and the rate at which the assistant escalates uncertain cases. Include unseen pipeline names, different error phrasings, and deliberately ambiguous incidents.

What success looks like

The fine-tuned model improves the target task without increasing unsafe automation. It produces the schema reliably, recognizes uncertainty, and does not claim that it checked a production system unless a real authorized tool returned that result.

16. Practical Fine-Tuning Checklist

Before training

  • The problem is a behavior / skill problem, not just a need for fresh factual knowledge.
  • Prompt engineering and a baseline have been tested first.

During training

Before production

  • The candidate beats the base model on the actual target metric.
  • General capability, safety, privacy and regression tests pass.

  • Versioning, monitoring, staged rollout and rollback are ready.
17 · Advanced parameter efficiency

17. LoRA and QLoRA: Technical Deep Dive

This chapter adds the parameter-count intuition, adapter-placement choices, and quantization details that help explain why LoRA and QLoRA can reduce the cost of adapting large models.

17.1 Understand the parameter-count reduction

Suppose a dense layer has a pretrained weight matrix W with dimensions d_out × d_in. Full fine-tuning can update every entry. LoRA represents the update using two smaller matrices whose inner dimension is the rank r:

A ∈ ℝr × din    B ∈ ℝdout × r
LoRA trainable parameters = r × din + dout × r = r(din + dout)

Worked example: a 4096 × 4096 dense matrix contains 16,777,216 weights. A rank-8 LoRA update uses 8 × (4096 + 4096) = 65,536 trainable values for that matrix pair. This is approximately 256 times fewer trainable values for that layer update. The total adapter still depends on how many modules receive LoRA layers.

17.2 Where can LoRA adapters be attached?

Target moduleWhat it influencesPractical consideration
Query / key projectionsAttention matching and which information tokens attend toCommon adaptation targets in transformer attention layers.
Value / output projectionsInformation carried through the attention operationOften included with query and key projections.
MLP / feed-forward projectionsFeed-forward transformations within transformer blocksAdding these modules increases adapter capacity and resource use.
Embedding / output layersToken representations or vocabulary output mappingMore specialized; verify model and PEFT support before targeting them.

Names such as q_proj, k_proj, v_proj, and o_proj are architecture conventions, not universal names. Inspect the model's module tree and check its fine-tuning guidance rather than copying a target-module list blindly.

17.3 Tune rank, alpha, dropout, and target modules together

  • Rank (r): controls the dimensionality and capacity of the low-rank update. A larger rank adds trainable parameters and compute.
  • Alpha (lora_alpha): scales the adapter contribution. A common scaling form is related to alpha / rank, though LoRA variants may use different rules.
  • Dropout (lora_dropout): regularizes the adapter path in supported implementations and may help in small-data settings.
  • Target modules: determine where adapters are inserted. More target layers can add capacity but also increase memory and change optimization behavior.

Do not tune rank in isolation. Compare a small set of adapter configurations using the same dataset, training budget, and held-out evaluation suite.

17.4 What QLoRA quantizes—and what it does not

In the common QLoRA design, pretrained base weights are stored in a low-bit representation, often 4-bit, and remain frozen. LoRA adapter parameters are trainable at a suitable higher precision. During the forward computation, quantized weight blocks may be dequantized into a supported compute dtype as needed. Therefore, “4-bit fine-tuning” does not mean every operation, gradient, activation, and trainable parameter is represented in 4 bits.

  • NF4: a 4-bit data type designed for normally distributed model weights.
  • Double quantization: quantizes quantization constants to reduce the memory overhead associated with storing them.
  • Paged optimizers: in supported implementations, help manage memory spikes by using paging mechanisms.
Important distinction QLoRA reduces memory used to store the frozen base weights. It does not eliminate activation memory, long-context attention cost, or the need for compatible kernels and hardware. A long sequence can still cause an out-of-memory failure with QLoRA.

17.5 Saving, merging, and distributing adapters

  • An adapter checkpoint usually contains adapter weights and configuration, not a full duplicate of the pretrained base model.
  • Inference requires a compatible base-model revision, tokenizer, chat template, and adapter configuration.
  • Some supported workflows can merge LoRA updates into the base weights to simplify serving. Check whether the architecture and quantization mode support the intended merge operation.
  • Keep the original adapter artifact even after creating a merged checkpoint; it supports reproducibility, comparison, and rollback.
18 · Data design and governance

18. Advanced Dataset Engineering

A dataset should encode a consistent behavior specification and cover the range of inputs the production model will encounter—not merely contain many examples.

18.1 Write a behavior specification before creating examples

Give annotators and reviewers a short, stable specification. Define:

  • The task and the inputs available to the model.
  • Allowed output values, required fields, format, and tone.
  • How the model should express uncertainty, ask for clarification, or abstain.
  • Refusal and escalation rules, including borderline examples.
  • What counts as a correct, partially correct, or unacceptable answer.

This reduces contradictory labels and makes future dataset revisions easier to review.

18.2 Use a coverage matrix to expose gaps

For a support-ticket classifier, define input dimensions before sampling records. The following is an illustrative coverage matrix:

DimensionCoverage examplesWhy it matters
Ticket categoryBilling, technical, account access, delivery, cancellation, otherChecks that important categories are represented.
PriorityLow, medium, high, urgent—with explicit definitionsReduces label drift between annotators.
Input qualityClear, incomplete, misspelled, multilingual, contradictoryTests behavior on realistic, imperfect inputs.
Conversation stateFirst message, follow-up, correction, reopened issueTests use of conversation history.
Boundary casesOut-of-scope requests and unclear cases needing escalationTeaches the model when not to force a classification.

Balance the dataset deliberately. Do not allow the largest or easiest-to-collect category to dominate without checking whether that reflects the production distribution and the task's risk profile.

18.3 Negative examples and rejected responses

Ordinary SFT generally trains on desired completions. A rejected answer should not simply be mixed into the SFT targets as though it were correct. Negative examples are useful when represented in a training objective designed for them—for example, chosen/rejected pairs for DPO or scored candidates for reward-based optimization.

A useful rejected response is plausible but inferior for a specific reason, such as being incomplete, unsupported, incorrectly formatted, or missing an escalation. Avoid obviously nonsensical rejected answers that teach little about the real decision boundary.

18.4 Synthetic data: use it as candidate data

LLM-generated examples can expand coverage, create paraphrases, and produce candidate edge cases. However, synthetic data may inherit the generator's errors, biases, style, and blind spots. A practical review pipeline is:

  1. Generate candidate examples from a written task specification.
  2. Apply deterministic checks wherever possible, such as JSON parsing, allowed-label validation, and field constraints.
  3. Use independent model review or expert review for semantic correctness.
  4. Deduplicate against existing training data and held-out evaluation cases.
  5. Record provenance so human-authored and synthetic data can be analyzed separately.

18.5 Measure annotation agreement

For subjective labels, ask multiple annotators to label a subset of examples. Measure agreement and inspect disagreements. If experts disagree because the guideline is ambiguous, revise the guideline and resolve the policy before scaling annotation. A model cannot reliably learn a crisp decision boundary from inconsistent labels unless the ambiguity is explicitly represented and handled.

18.6 How much data is enough?

There is no universal data-count threshold. The supplemental notes suggest that a narrow first experiment may begin with dozens to a few hundred carefully reviewed examples, then expand based on measured error patterns. This is a starting heuristic, not a guarantee or a rule for broad tasks. More diverse examples are usually needed for long-tail coverage, multiple languages, broad task definitions, or high reliability requirements.

Use a learning curve: train or evaluate with increasing dataset sizes and plot held-out quality against the number of examples. If performance is still improving materially, more relevant data may help. If it has plateaued, investigate label quality, model capacity, task definition, or the evaluation setup.

18.7 Version the dataset as an engineering artifact

Preserve the raw source, normalized examples, transformation code, label schema, train/validation/test assignments, and quality-review status. Record why examples were added or removed. Dataset hashes or immutable version identifiers help distinguish a model change from a data change when experiment results differ.

19 · Training infrastructure

19. Compute Planning and Training Operations

19.1 What consumes GPU memory?

Training memory is not just the model weights. A useful mental model includes:

  • Parameters: model weights and trainable adapter weights.
  • Gradients: gradient tensors for trainable parameters.
  • Optimizer state: for example, first and second moments maintained by Adam-like optimizers.
  • Activations: intermediate tensors retained for backpropagation. Batch size and sequence length strongly affect this component.
  • Temporary workspace: attention kernels, communication buffers, and allocator overhead.

PEFT substantially reduces trainable parameters, gradients, and optimizer state. It does not remove the need to run the frozen transformer through the forward path or retain/recompute activations. Long context can therefore remain expensive even when using LoRA.

19.2 Techniques for fitting a training run into hardware

TechniqueWhat it helps withTrade-off / caution
Mixed precision (BF16 / FP16)Can reduce memory use and improve throughput.Hardware support and numerical stability matter; BF16 and FP16 are not interchangeable on every setup.
Gradient accumulationBuilds a larger effective batch from smaller micro-batches.More forward/backward passes occur before an optimizer update and throughput may change.
Gradient checkpointingReduces activation memory.Some forward computations are repeated during backpropagation, increasing compute time.
Quantized base weightsReduces memory needed to store a frozen base model.Requires compatible kernels and backends; may involve performance or quality trade-offs.
Shorter sequence lengthReduces activation and attention costs.May remove important context or truncate the target answer.
Distributed trainingShares data, model components, or model state across devices.Adds communication, configuration, and debugging complexity.

19.3 Data parallelism versus model sharding

Data parallelism: model replicas process different batches and synchronize gradients. Each device works on a different portion of the batch.

Model sharding: different parts of the model or its training states are distributed across devices. Frameworks may combine data parallelism with tensor, pipeline, or fully sharded approaches.

For a small LoRA experiment, a single GPU may be easier to configure and debug. Larger models may require distributed strategies. Choose the simplest setup that satisfies memory and throughput requirements.

19.4 Reproducibility metadata

Record the random seed, exact base-model revision, dataset version or hash, tokenizer, chat template, training-code revision, package versions, hardware, precision, optimizer, scheduler, and all trainer arguments. Bitwise reproducibility may not be possible across hardware and kernels, but complete run metadata makes comparisons much more defensible.

20 · Evaluation design

20. Advanced Evaluation: Beyond One Aggregate Score

20.1 Build an evaluation matrix

Organize the held-out test set into slices that represent capability, input quality, and risk. For a ticket classifier, an evaluation matrix could include:

Test sliceExampleWhat it reveals
Common casesClear billing complaintCore task performance.
Rare classesAccount takeover concernLong-tail performance.
Ambiguous inputs“It doesn't work”Uncertainty and escalation behavior.
Conflicting contextCustomer corrects earlier detailsConversation-state handling.
Adversarial instructionsTicket text asks the model to ignore classification rulesInstruction hierarchy robustness.
Format stressLong text, quotes, braces, unusual charactersParser and schema reliability.
Out-of-scope requestsGeneral product advice requestBoundary handling and appropriate abstention.

Report both the overall metric and the per-slice results. An aggregate score can hide a serious regression in a rare but high-impact category.

20.2 Sample size and confidence intervals

A metric measured on a small test set is uncertain. For example, 90% accuracy on 50 cases can move substantially when only a few predictions change. Report the number of evaluated examples and, when the decision warrants it, an uncertainty interval around the measured score. A Wilson interval is often preferable to a simple normal approximation for a binomial proportion, particularly with small samples or scores near 0% or 100%.

Interpret small benchmark gains carefully A two-point improvement on a small test set may be noise rather than a real quality gain. Use a representative sample size, compare the same examples, and consider the practical impact of the errors—not only the point estimate.

20.3 Pairwise human evaluation

For subjective outputs, show reviewers two anonymized responses to the same prompt. Randomize the order and ask which response is better under a defined rubric. Include options such as tie and both poor when appropriate. Blind comparisons reduce brand or model-identity bias. Report preference rates alongside task-specific failure categories and reviewer agreement.

20.4 LLM-as-a-judge: useful, but not ground truth

A model grader can scale evaluation, but it can prefer longer answers, share the candidate model's biases, miss subtle factual errors, or be influenced by which answer appears first. Improve reliability by:

  • Using a fixed, explicit rubric with observable criteria.
  • Randomizing candidate order and testing for position bias.
  • Calibrating grader results against human judgments.
  • Auditing disagreements and periodically reviewing samples manually.
  • Preferring deterministic parsers, exact checks, and executable tests for objective requirements.

20.5 Define regression gates before deployment

Require the candidate to meet minimum thresholds on the target task and stay within acceptable bounds for safety, general capability retention, formatting, and latency. A model that improves one metric but breaks a critical refusal, escalation, or tool-call behavior should not pass release approval.

22 · Interview preparation

22. LLM Fine-Tuning Interview Questions

Q1. What is fine-tuning?

Additional training of a pretrained model on task-specific examples or feedback to adapt its parameters to a target task, domain, format, or behavior.

Q2. What is the difference between pretraining and fine-tuning?

Pretraining develops broad language and model capabilities from large-scale data. Fine-tuning starts from that pretrained model and adapts it to a narrower task or desired behavior.

Q3. What is supervised fine-tuning (SFT)?

SFT trains on input-target demonstrations, typically increasing the likelihood of the desired output tokens using a token-level cross-entropy objective.

Q4. What is LoRA?

LoRA is a parameter-efficient method that freezes the base weights and learns low-rank update matrices. This reduces the number of trainable parameters and the associated gradient and optimizer-state memory.

Q5. What is the difference between LoRA and QLoRA?

LoRA trains adapters while keeping the base model frozen, typically in its normal model precision. QLoRA additionally stores the frozen base weights in a quantized representation, commonly 4-bit, to reduce base-weight memory use.

Q6. What is DPO, and how does it differ from SFT?

SFT learns from a desired target answer. DPO learns from preference pairs such as a chosen and a rejected response, directly optimizing relative preferences without the separate reward-model stage used in conventional RLHF.

Q7. When would you choose RAG instead of fine-tuning?

Choose RAG when an application needs fresh, private, frequently changing, or source-citable information. Fine-tuning is generally better suited to stable behavior, style, and repeated task patterns.

Q8. Why can training loss be misleading?

Training loss measures how well the model fits its training targets. It does not prove generalization, factual correctness, safety, or user value. Held-out evaluation and regression tests are necessary.

Q9. What is catastrophic forgetting?

It is degradation of previously learned capabilities during further training, often associated with narrow data or overly aggressive parameter updates.

Q10. How do you decide whether fine-tuning is worth the cost?

Compare the tuned model with a strong prompt/application baseline on representative held-out data. Consider quality, safety, latency, and total cost, and fine-tune only when the measured benefit justifies the extra lifecycle complexity.
